# RAG Agent 项目面试标准答案

本文面向当前“企业售后知识库 RAG 智能体”项目，整理面试中最值得回答的问题。答案以本项目真实实现和评测结果为依据，用于复习和组织表达，不建议逐字背诵。

回答项目问题时，建议遵循这个顺序：

1. 先说结论。
2. 再说本项目怎样实现。
3. 接着说明为什么这样设计。
4. 最后主动说明限制和后续改进。

## 一、项目总览与 RAG 主链路

### 1. 请介绍一下这个项目

标准答案：

这是一个面向扫地机器人售后场景的 RAG 智能体学习与作品集项目。系统可以摄取 TXT、Markdown 和 PDF 资料，将文本规范化、分片并写入 Chroma；用户提问时，系统先检索相关分片，再让通义千问仅依据检索证据生成回答，并对引用编号做程序化校验。

在普通知识问答之外，项目还使用 LangGraph 编排设备查询和工单创建流程，使用 SQLite Checkpoint 保存会话状态，并通过 `interrupt()` 在工单写入前等待人工确认。用户、设备、订单和工单都属于本地模拟数据，不代表真实企业系统。

项目的重点不是简单调用大模型，而是建立一条可追溯、可拒答、可评测、可测试的 RAG 与 Agent 链路。

### 2. RAG 的完整执行流程是什么

标准答案：

这个项目将 RAG 分成离线入库和在线问答两条链路。

离线入库链路：

```text
文件发现
→ TXT、Markdown、PDF 加载
→ 编码识别和文本规范化
→ 生成稳定文档 ID、校验值和版本
→ 按页、标题和字符范围分片
→ 过滤目录类低价值分片
→ 批量计算 Embedding
→ 按稳定 chunk ID 写入 Chroma
→ 在 SQLite 记录文档状态、版本和入库任务
```

在线问答链路：

```text
用户问题
→ Query Embedding
→ Chroma Top-K 相似度检索
→ 返回分片、来源、页码、标题和分数
→ 在上下文预算内组装编号证据
→ 将证据标记为不可信数据
→ 模型输出结构化 JSON
→ 校验回答状态和引用编号
→ 输出带来源回答，或者明确拒答
```

这两条链路之间通过稳定的文档 ID、分片 ID、来源和页码建立追溯关系。

### 3. Embedding 模型和聊天模型有什么区别

标准答案：

Embedding 模型把文本映射为向量，主要解决“语义上哪些文本更接近”的问题。本项目用它处理文档分片和用户查询，供 Chroma 做相似度检索。

聊天模型接收指令、问题和检索证据，生成自然语言或结构化结果，主要负责意图分类、字段提取和回答生成。

两者不能互相替代：Embedding 模型不负责组织答案，聊天模型也不适合逐条扫描整个知识库寻找相关文本。RAG 的价值就是先用 Embedding 缩小证据范围，再让聊天模型基于证据生成回答。

### 4. 文档为什么需要分片

标准答案：

整篇文档通常太长，无法全部放入模型上下文；即使能够放入，文档级向量也会混合多个主题，导致局部信息被稀释。因此需要把文档切成语义相对集中的分片。

分片太大时，一个向量包含多个主题，精确问题可能无法召回；上下文也更昂贵。分片太小时，完整语义容易被拆散，召回结果缺少必要条件。重叠可以减少边界截断，但过大又会产生重复信息和相似分片竞争。

本项目使用标题感知的递归字符切分，并保留页码、标题层级和字符范围，使分片不仅能检索，还能追溯到原文。

### 5. `chunk_size` 和 `chunk_overlap` 应该怎样确定

标准答案：

它们不应该凭经验一次决定，而应该通过数据集实验确定。

我会选择多组 `chunk_size` 和 `chunk_overlap`，比较：

- 分片数量和长度分布。
- Recall@K 和 MRR。
- 正确分片是否完整包含回答条件。
- 重复分片是否挤占 Top-K。
- 上下文字符数、生成延迟和成本。

然后查看失败样本，区分问题来自分片过长、边界切断、标题丢失还是原始资料本身缺失。当前项目仍有两条安全类问题因为某页分片过长、主题被稀释而漏检，这说明参数仍有改进空间。

### 6. 为什么要保留页码、标题和字符范围

标准答案：

这些字段构成可追溯性。页码用于向用户展示来源并进行页级评测；标题帮助理解分片所属主题；字符范围可以把分片定位回规范化后的原文。

如果只有向量和文本，没有这些元数据，即使回答看起来正确，也很难核验来源、分析错误或定位切分问题。可追溯性既服务用户，也服务开发者排障和离线评测。

### 7. 为什么 Chroma 和 SQLite 承担不同职责

标准答案：

检索时，系统先用与文档相同的 Embedding 模型把问题转换成向量，再由 Chroma 比较 Query 向量和分片向量的余弦距离，选出距离最小的 Top-K；本项目把它转换为 `score = 1 - distance`，分数越高表示向量方向越接近。相似度只表示语义接近程度，不等于答案正确概率。

Chroma 适合保存向量并执行这种相似度检索，因此保存分片向量及检索需要的元数据。SQLite 适合结构化事务数据，因此保存文档版本、校验值、入库任务、业务模拟数据、会话归属和 Checkpoint。

将两者分开后，向量索引可以重建，而文档状态和业务记录仍有明确的结构化来源。代价是必须维护一致性，例如删除文档时要同时删除向量和元数据，重建索引时要清理已经不存在的文件。

### 8. 文档更新后如何避免新旧向量同时存在

标准答案：

本项目先根据来源生成稳定文档 ID，根据内容生成校验值和版本。入库时会比较已有记录的校验值和 Embedding 模型；完全未变化时跳过重复计算。

内容变化时，项目按稳定 chunk ID 执行 upsert，然后获取该文档当前所有向量 ID，删除本次切分结果中已经不存在的旧 ID，最后更新 SQLite 中的文档状态。

重建索引时还会扫描已经从原始目录删除的文件，同时清理 Chroma 和 SQLite 中的残留记录。核心思想不是“再次插入”，而是让索引最终状态与当前文档集合一致。

### 9. 检索结果怎样变成模型上下文

标准答案：

Retriever 返回按相似度排序的 `RetrievalHit`，每条包含分片、分数和排名。回答层在字符预算内选取前面的命中项，将它们编号为 `[1]`、`[2]`，并附上来源、页码和标题。

模型只能从这些编号资料中选择引用。程序同时保存“真正放进上下文的命中集合”，后续只允许引用这个集合内的编号。这样可以避免模型引用检索到但没有进入上下文的内容，也避免引用不存在的来源。

### 10. 为什么不能把模型原始输出直接展示给用户

标准答案：

模型输出是不可信的，可能出现非 JSON、空答案、未知状态、虚构引用或越界引用。项目要求模型返回包含 `status`、`answer`、`reason` 和 `citations` 的 JSON，程序再做严格解析和引用校验。

只有状态为已回答、正文非空且至少有一个有效引用时，答案才会被释放。没有有效引用时，即使文字看起来合理，也会拒绝输出。流式调用同样只把原始增量用于进度展示，最终用户看到的是校验后的结果，而不是未经验证的 Token 流。

## 二、检索和回答评测

### 11. Recall@K 和 MRR 分别衡量什么

标准答案：

Recall@K 判断前 K 条检索结果中是否出现了预期证据。在本项目的页级评测里，只要 Top-K 中出现预期页，就记为命中。它回答的是“正确证据有没有被找回来”。

MRR 使用第一个正确结果排名的倒数。例如正确页排第一得 1，排第二得 0.5。它回答的是“正确证据排得是否足够靠前”。

Recall@K 高但 MRR 低，说明正确证据能够被召回，却经常排在后面，容易被上下文预算截断或被无关分片干扰。

### 12. 回答率、引用正确率、拒答正确率和决策正确率有什么区别

标准答案：

- 回答率：可回答问题中，系统最终实际回答了多少。
- 引用正确率：已经回答的问题中，引用页是否符合评测集预期。
- 拒答正确率：不可回答问题中，系统正确拒答了多少。
- 决策正确率：把“可回答时回答”和“不可回答时拒答”合并后的总体决策正确比例。

只看回答率可能鼓励系统什么都回答；只看拒答正确率又可能鼓励系统全部拒答。因此必须联合观察，并进一步检查引用是否真的支持答案。

### 13. 为什么忠实度只是代理指标

标准答案：

当前项目的忠实度通过答案与引用分片之间的字符 n-gram 覆盖程度近似计算。它能发现答案与证据完全无关的情况，但不能真正判断事实逻辑。

一个错误答案可能大量复用资料原词，从而得到较高分；一个正确的同义改写也可能得到较低分。因此它适合作为告警和对比指标，不应被描述为真实事实准确率。更严格的方案可以增加人工标注、声明级证据对齐或独立评审模型，但仍需要校准。

### 14. 为什么评测集必须包含不可回答问题

标准答案：

RAG 系统不仅要“会回答”，还要知道什么时候没有依据。如果评测集只有可回答问题，就无法验证拒答能力，也无法发现系统为了提高回答率而编造结论。

不可回答问题用于检查检索阈值、Prompt 约束、模型的不足判断和引用校验能否共同阻止无依据回答。本项目当前 6 条不可回答问题全部被正确拒答，但样本数量仍然较小，不能据此声称覆盖了全部越界问题。

### 15. 为什么一次指标上涨不能直接归因于代码修改

标准答案：

生成式模型存在运行波动。同一份代码、同一份资料和同一个问题，也可能得到不同措辞或引用选择。因此修改前后各运行一次，不足以证明因果关系。

应当固定数据集、模型、配置和温度，保存逐题结果，进行多次重复实验，并区分确定性的检索指标和可能波动的生成指标。当前项目第二次引用正确率高于第一次，其中部分来自模型对具体题目的输出变化，所以不能把全部提升归功于引用修复代码。

### 16. 如何分析一条 RAG 失败样本

标准答案：

我会按数据流逐层定位，而不是直接修改 Prompt：

1. 原始资料是否真的包含答案，评测标注是否正确。
2. 加载和规范化后文字是否完整，页码是否正确。
3. 分片是否把问题需要的条件拆散，标题和字符范围是否保留。
4. 正确分片是否进入 Top-K；若没有，检查 Query、Embedding 和无关分片竞争。
5. 正确分片已经召回时，是否进入上下文预算。
6. Prompt 是否清楚要求仅依据资料作答。
7. 模型是否正确生成正文和引用。
8. 校验或引用修复是否错误拒绝、错误接受或错误映射。

只有先确定失败发生在哪一层，才能选择调整资料、分片、检索、Prompt、模型还是校验规则。

### 17. Top-K、阈值和重排分别解决什么问题

标准答案：

Top-K 控制候选证据数量：太小容易漏掉正确证据，太大会增加噪声和上下文成本。

阈值过滤明显不相关的低分结果，但相似度不是事实正确性的概率。本项目中可回答与不可回答问题的最高分区间有重叠，所以不存在一个阈值能完全分开两类问题。

重排是在初步召回后，用更精细的模型重新比较 Query 和候选分片，主要解决“召回到了但排序不够好”。当前项目尚未实现重排，因此可以作为后续改善 MRR 和长分片漏检的方向，但必须通过评测验证收益和延迟成本。

### 18. 项目的引用修复解决了什么问题

标准答案：

评测发现模型有时会把资料表格中的数字，例如故障序号 8，误写成引用 `[8]`。当上下文实际没有第 8 个来源时，这会被引用校验判为越界。

项目先区分两种情况：越界数字确实出现在证据正文中，可能是表格序号混淆；越界数字完全不在证据中，更可能是编造。只有前一种且没有混入编造引用时，系统才允许第二次模型调用。

修复调用只能选择 `SOURCE-A`、`SOURCE-B` 之类与数字空间分离的临时标签，不能修改原答案正文。程序再把标签映射回已检索来源并重新校验。这样修复的是引用选择，不是偷偷重写事实。

## 三、LangChain、LangGraph 和业务 Agent

### 19. LangChain 和 LangGraph 有什么区别

标准答案：

在本项目中，LangChain提供局部能力组件，例如 Prompt、输出解析、文本切分和 LCEL 最小链路。LangGraph负责有状态工作流，包括状态、节点、边、条件路由、循环限制、Checkpoint、暂停和恢复。

可以把 LangChain 理解为“一个步骤内部怎样调用模型和处理数据”，把 LangGraph 理解为“多个步骤按照什么确定性结构协作”。两者不是替代关系。

### 20. 为什么有些流程必须写成图，不能只依靠 Prompt

标准答案：

Prompt只能影响模型行为，不能提供强制性的业务保证。模型可能误分类、漏掉字段、错误声称用户已经确认，或者生成未授权的工具参数。

状态图把允许的节点和边固定在代码里。例如信息收集不能直接跳到工单创建，待确认节点之后才可能进入写节点；失败、澄清和知识问答都有明确终点。这样可以通过检查图结构和单元测试证明不存在某些危险路径，而不是依赖模型“尽量遵守”。

### 21. Agent 的意图路由怎样工作

标准答案：

系统先用聊天模型把问题分类为知识问答、设备查询、工单或未知意图，并返回置信度和理由。图根据分类进入固定分支。

项目还保留确定性纠偏：当上下文已经明确设备，用户只说“它还在保修吗”这类指代追问时，如果模型没有选设备分支，代码可以根据会话信息纠正路由，并在 trace 中明确记录“从哪个意图重路由”。

这体现了一个原则：模型负责语义判断，但明显可验证的业务规则可以由代码兜底，而且兜底行为必须可观察。

### 22. Tool Calling 的参数如何生成和校验

标准答案：

模型可以负责从自然语言中提取设备编号、故障描述和联系方式，但提取结果不会直接传给数据库。项目先解析模型返回的 JSON，再通过 Pydantic 参数模型检查字段类型、必填关系和格式。

进入工具后还会依次检查：调用角色是否允许该工具、用户或设备是否存在、记录归属是否匹配、写操作是否明确确认。工具失败统一返回稳定错误码和 `retryable`，不会把异常字符串伪装成正常业务结果。

因此模型产生参数不等于模型获得执行权限。

### 23. 为什么工单创建必须人工确认

标准答案：

工单创建是有副作用的写操作，可能触发后续人工处理，因此不能让模型根据自然语言猜测用户是否同意。

项目先收集并展示工单草稿，再在 `ticket_create` 节点调用 `interrupt()` 暂停。只有调用方用结构化恢复载荷明确传入 `confirmed is True` 才执行写入；取消、缺字段、字符串 `"true"` 或其他值都不会写库。

### 24. 为什么 `interrupt()` 必须出现在写操作之前

标准答案：

LangGraph 的中断节点恢复时会从节点开头重新执行。如果在 `interrupt()` 前已经写数据库、发消息或调用外部接口，恢复时副作用可能执行第二次。

因此本项目让中断发生在任何工具调用之前。取消时完全没有写入；恢复后才调用创建工具。即使恢复后的工具失败，也不会留下确认前的半成品操作。

### 25. 为什么图层和工具层都要检查确认

标准答案：

这是纵深防御。图层保证正常工作流不能绕过待确认步骤；工具层保证即使未来有人直接调用工具、错误连接节点或新增入口，也不能在 `confirmed=False` 时写入。

两层检查解决的故障范围不同，任何一层单独存在都不够稳健。项目还用测试分别证明图中不存在危险直达边，以及工具在未确认时拒绝写入。

### 26. 为什么写操作需要幂等键

标准答案：

网络超时、进程重试或用户重复点击都可能让同一个创建请求执行多次。没有幂等保护时，会生成重复工单。

项目根据稳定的工单草稿生成幂等键，也允许调用方显式提供。创建前先按键查询已有工单；存在时返回原记录并标记 `created=False`，不存在时才创建。这样调用者可以安全重试。

## 四、会话记忆与 Checkpoint

### 27. 多轮对话状态如何隔离、持久化和恢复

标准答案：

每条会话使用 `thread_id` 作为 LangGraph Checkpoint 键。SQLite Checkpointer保存每个 super-step 的状态、通道值、父指针和中断写入，因此进程退出后仍能读取同一会话并继续执行。

应用层另外维护 `thread_id → user_id` 归属。因为 LangGraph只把 `thread_id` 当作不透明字符串，它本身不知道用户概念；如果没有应用层归属检查，“隔离”就只是调用方自觉使用不同 ID，而不是真正的访问控制。

### 28. 完整历史和最近 8 条消息窗口有什么区别

标准答案：

完整历史保存在 Checkpoint 中，用于恢复、审计和显示。真正进入本轮 Prompt 的只有最近 8 条消息，并可按配置覆盖。

这样既保留会话，又避免 Prompt 随轮次无限增长和旧内容持续干扰当前问题。窗口是上下文使用边界，不是数据保存边界。

### 29. 短期记忆和长期偏好有什么区别

标准答案：

短期记忆属于某条会话，例如上一轮问的是哪台设备；长期偏好属于用户，例如倾向使用邮箱联系。

短期消息随 `thread_id` 保存在 Checkpoint，长期偏好按 `user_id` 单独保存在 SQLite。清除某条会话时不删除用户偏好，因为两者生命周期和归属不同。

### 30. Streamlit `session_state` 为什么不能替代 Agent Checkpoint

标准答案：

`session_state` 主要服务当前浏览器会话和界面 rerun，适合保存控件状态、页面消息和一次性 UI 结果。它不是 Agent 执行历史的持久化协议，进程重启、换浏览器或从 CLI 调用时无法可靠恢复图状态。

Checkpoint与 LangGraph执行模型绑定，能够保存节点执行进度、中断和恢复信息。UI 状态和业务工作流状态职责不同，不能混为一谈。

### 31. 为什么项目自实现 SQLite Checkpointer，而不是直接使用内存或官方后端

标准答案：

`InMemorySaver` 无法满足进程重启后继续会话，因此只能作为测试替身。项目选择继承 `BaseCheckpointSaver`，使用标准库 `sqlite3` 实现同步 Checkpointer，减少额外依赖，并让学习者真正理解 Checkpoint 的数据结构和恢复过程。

代价是需要自行维护约 400 行实现，而且单连接加锁限制同进程并发写吞吐。若未来需要异步、多进程或更高并发，应优先评估官方后端或外部持久化服务，而不是继续扩展这份教学实现。

## 五、Provider、Python 工程和测试

### 32. 为什么要做 Provider 抽象

标准答案：

业务代码只依赖 `ChatModel` 和 `EmbeddingModel` 协议，不直接依赖通义千问 SDK。Qwen只是其中一个适配器，配置层负责组装具体实例。

这样做可以隔离供应商字段和异常体系，方便替换模型，并允许 Fake Provider在无网络、无密钥环境中运行确定性测试。代价是项目需要自行维护请求、响应解析和错误分类。

### 33. 为什么项目用 httpx 直连兼容端点

标准答案：

选择 httpx 是为了控制请求体、超时、重试、错误分类、日志和流式解析，同时避免引入供应商 SDK 或额外 OpenAI SDK 耦合。

相比完全自建 HTTP 客户端，httpx 已经提供连接池、代理、重定向和超时语义。相比供应商 SDK，它让项目的协议和错误类型保持稳定。风险是兼容端点字段发生变化时，需要项目自己更新 Pydantic 响应模型和测试。

### 34. 哪些模型错误可以重试

标准答案：

通常连接中断、部分超时、限流和服务端暂时错误可以按有限次数及退避策略重试；鉴权失败、非法参数和确定性的响应格式错误通常不应盲目重试。

项目把超时、连接、限流、服务端、鉴权、请求和响应错误分类，调用方根据稳定错误码决定重试、拒答或报告错误。重试次数必须有限，日志不能泄露 API Key。

### 35. Fake Provider 有什么价值

标准答案：

Fake Provider不是简单返回固定字符串，而是模型边界上的测试替身。它可以提供确定的回答、向量、流式增量或错误，使测试不受网络、密钥、限流和模型波动影响。

这样可以稳定测试入库、检索、路由、引用校验和降级逻辑。真实 Qwen 集成测试仍然保留，但默认跳过，只在明确开启联网测试时执行。

### 36. 项目为什么使用依赖注入

标准答案：

Retriever、聊天模型、Embedding 模型、Repository、Checkpointer 和权限对象由入口组装并传入，而不是在节点内部直接创建。

这让业务逻辑与具体基础设施解耦，测试可以替换为 Fake、临时数据库或内存实现，也能避免全局状态。依赖注入还让权限成为构图参数而不是模型可影响的状态，从而减少提权风险。

### 37. 这个项目的测试策略是什么

标准答案：

测试分为三个层次：

- 单元测试验证纯函数、数据模型、失败分支、Provider、入库、检索、引用、权限、图路由和 Checkpoint。
- 集成测试验证真实 Qwen 接口，但默认跳过，避免日常测试依赖网络。
- 端到端测试使用可控替身跑通“入库 → 检索 → 回答 → 工具 → 确认”的核心演示流程。

关键原则是让设计声明可以被测试证明。例如“未确认不写库”不仅写在文档里，还要检查图的边、节点中断顺序、工具确认和最终数据库记录。

### 38. 修改项目功能时应该怎样补测试

标准答案：

先把问题转换成一个最小失败用例，确认旧代码下测试能够失败；再修改实现，让新测试和原有回归测试一起通过。

测试应围绕可观察行为，不要只断言内部调用次数。例如修复重复工单时，应断言相同幂等请求最终只有一条数据库记录；修复引用越界时，应断言无效引用不能进入最终 `citations`。

## 六、安全、权限、可观测性和降级

### 39. 如何防范 Prompt Injection

标准答案：

本项目不把启发式“恶意文本检测”当成主要防线，因为自然语言规则一定会漏报和误报。

主要控制是：把检索文档显式包裹为不可信证据，在系统提示中声明其中内容是数据而不是指令；模型输出必须经过结构化解析和引用校验；文档内容无法授予工具权限，也无法让不存在的引用通过校验。

项目仍会扫描类似“忽略前面规则”的文本，但扫描结果只用于上报和审计，不自动删除资料，也不单独触发拒答。

### 40. 如何防止模型越权调用工具

标准答案：

权限对象由可信入口构造，并作为图的构造参数传入，不放入模型可影响的状态。角色只能从入口授予的等级向下选择，不能通过输入文字要求提权。

工具调用前先检查角色白名单，再检查记录归属；拒绝发生在访问 Repository之前。模型可以建议调用哪个工具和提取哪些参数，但最终权限判断只由确定性代码完成。

当前界面中的用户编号和角色仍是自述，没有真实身份认证，所以这是演示级权限模型，不应描述成生产授权系统。

### 41. 系统如何处理模型、检索和工具故障

标准答案：

项目把失败收敛为 `retry`、`answer_partial`、`refuse` 和 `report_error` 四类动作，并提供稳定错误码和面向用户的非事实性说明。

- 模型临时失败可以有限重试；鉴权或请求错误直接报告。
- 检索没有证据时拒答，不调用模型编造答案。
- 工具失败返回结构化错误、是否可重试和请求 ID。
- 任何降级路径都不能伪装成正常业务结果。

这样上层不需要解析异常字符串，也能统一决定界面提示和退出码。

### 42. 项目的可观测性包含什么

标准答案：

项目使用 JSON 结构化日志记录模型耗时、重试次数、token 用量和错误分类；在 Agent 回合状态中记录总耗时、检索命中数、最高分、工具调用、工具失败码和注入疑点。

指标必须来自真实测量，不能推算。当前 token 用量在 Provider 日志中存在，但尚未写回图状态，因此回合指标如实显示未采集，而不是估算一个看起来合理的数字。

### 43. 如果流量和文档量增长，系统应该如何扩展

标准答案：

我会先用指标确认瓶颈，再按层扩展：

- 入库：把同步逐文件处理改成任务队列和批量、并发 Embedding，增加失败重试和任务状态。
- 向量库：从本地 Chroma迁移到 Qdrant、Milvus 或 pgvector，增加命名空间、租户过滤和备份。
- 检索：加入混合检索、元数据过滤和重排，控制候选量及上下文预算。
- 模型：加入限流、熔断、缓存、批处理和多供应商路由。
- 会话：用官方持久化后端或外部数据库替代单连接 SQLite Checkpointer。
- 服务：把 Streamlit展示层与 FastAPI业务服务拆开，通过身份认证和服务端授权保护入口。
- 可观测性：加入分布式追踪、告警、成本和质量仪表盘。

不能直接声称当前项目支持高并发，因为目前没有并发压测和生产部署证据。

## 七、项目限制与诚实表达

### 44. 这个项目目前有哪些主要限制

标准答案：

第一，Streamlit界面没有真实身份认证，角色和用户编号由访问者自述，因此权限只能证明代码中的授权结构，不能证明真实身份安全。

第二，业务用户、设备、订单和工单全部是本地模拟数据，没有接入真实企业接口。

第三，自实现 SQLite Checkpointer采用单连接加锁，适合本地学习和演示，不适合直接宣称高并发。

第四，矢量轮廓 PDF 不支持 OCR；扫描版资料可能无法提取文字。

第五，相似度阈值不能完整区分可回答与不可回答问题，仍需要引用校验和拒答机制。

第六，忠实度是弱代理指标，评测集只有 49 条，仍需扩展样本和人工校验。

第七，token 用量尚未并入 Agent 回合指标。

### 45. 这个项目可以称为生产级系统吗

标准答案：

不能。它具备一些生产工程意识，例如配置隔离、结构化错误、权限白名单、幂等、Checkpoint、评测、测试、非 root 容器和持久卷，但缺少真实认证、真实业务接口、并发压测、服务级监控、备份恢复和线上运行证据。

更准确的表述是：这是一个按照企业场景约束设计、具有完整质量与安全闭环的学习及作品集项目，可以演示关键架构决策，但不是已经投入生产的系统。

### 46. 如果让你继续改进，优先做什么

标准答案：

我会优先做两件事。

第一，针对当前漏检样本改进分片和检索，通过扩大评测集、分片参数实验、混合检索或轻量重排提高 MRR，同时观察延迟和上下文成本，避免只追求单一指标。

第二，把身份认证和授权移到服务端可信入口，拆分 Streamlit与业务服务，确保角色不是用户自述。完成后再考虑高并发存储、异步任务和分布式追踪。

这个顺序先解决当前有证据的问题，再扩展尚未验证的生产能力。

## 八、面试现场的完整项目回答模板

### 47. 请用三分钟介绍项目的技术亮点

标准答案：

我做的是一个扫地机器人售后知识库 RAG 智能体。入库侧支持 TXT、Markdown 和 PDF，经过规范化和标题感知分片后写入 Chroma，同时用 SQLite维护文档版本和入库状态，因此文档更新时可以增量替换旧向量。

问答侧先做 Top-K 检索，再把带页码和来源的分片组装成编号证据。模型必须返回结构化结果，系统会校验回答状态和引用编号；没有可核验引用就拒答。项目还建立了 49 条评测集，测量 Recall@5、MRR、回答率、引用正确率和拒答正确率。评测发现相似度阈值无法完全区分可答与不可答问题，所以阈值只用于过滤明显无意义结果，最终边界由资料约束和引用校验承担。

Agent部分用 LangGraph把知识问答、设备查询和工单创建编排为显式状态图。工单写入前使用 `interrupt()` 真实暂停，恢复后才执行工具；工具层还会再次检查确认、权限和幂等键。会话通过 SQLite Checkpoint跨进程保存，并按用户校验 thread归属。

工程方面，项目使用 Provider协议隔离通义千问，Fake模型支持离线测试，并提供结构化日志、统一降级、Streamlit界面和非 root Docker Compose交付。当前仍是学习与作品集系统，没有真实认证、真实企业接口和高并发证明。

### 48. 这个项目最困难的问题是什么

标准答案：

最困难的不是调用模型，而是把“回答看起来不错”变成可验证的系统行为。

一个典型问题是模型把资料表格中的数字误当成引用编号。简单放宽引用校验会接受虚构来源，简单拒答又会损失本来正确的回答。我先通过逐题评测确认失败模式，再区分表格序号混淆和真正编造，只对前者触发第二次受限修复。修复模型只能选择与数字空间分离的来源标签，不能修改答案正文，最终标签仍由程序映射并校验。

这个过程体现了我的解决方式：先建立指标和失败样本，再缩小问题范围，设计最小修复边界，最后用自动化测试和重复评测验证，同时承认模型波动不能全部归因于代码。

### 49. 你从这个项目中学到了什么

标准答案：

第一，RAG质量主要取决于整条数据链路，Prompt只是其中一层。原始资料、分片、索引更新和检索排序都会影响最终回答。

第二，模型输出必须被当作不可信输入。结构化解析、引用校验、权限、人工确认和幂等都应该由确定性代码承担。

第三，没有评测就无法判断优化是否有效。平均指标之外还必须保存逐题结果并分析失败样本。

第四，工程边界和诚实表达很重要。能够运行 Docker不等于生产级，角色字段不等于真实认证，代理指标也不等于事实准确率。
