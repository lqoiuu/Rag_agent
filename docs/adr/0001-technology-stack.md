# ADR-0001：采用分层的 LangChain、LangGraph、Chroma 与 SQLite 技术方案

- 状态：已接受
- 决策日期：2026-09-10
- 适用阶段：阶段 0 起
- 决策范围：第一版企业售后知识库 RAG 智能体

## 背景

项目需要同时覆盖完整 RAG 数据链路和具有工具调用、人工确认、状态恢复能力的 Agent 工作流。它既要适合个人学习与本地演示，也要让每个模块可以独立测试、替换和解释。

主要约束：

- 本机与项目统一使用 Python 3.13，并逐项核验依赖兼容性。
- 首个模型供应商为通义千问，但业务代码不能绑定单一供应商。
- 第一版以本地运行和低运维成本为主。
- 知识回答必须可追溯，写操作必须受确定性流程保护。
- 用户、设备、订单和工单接口均为模拟实现。
- 最终需要 Streamlit 演示、自动化测试和 Docker Compose 复现。

## 决策

第一版采用以下分层技术方案：

| 领域 | 决策 |
|---|---|
| Python | Python 3.13 |
| 模型接入 | 通义千问作为首个实现，外部包裹自定义 Provider 协议 |
| RAG 组件 | LangChain |
| Agent 编排 | LangGraph |
| 向量存储 | Chroma 本地持久化 |
| 关系型与元数据存储 | SQLite |
| 数据校验与配置 | Pydantic 与 pydantic-settings |
| 前端 | Streamlit |
| 测试 | pytest |
| 代码质量 | Ruff 与 mypy |
| 交付 | Docker Compose |

职责边界：

1. LangChain 负责 Loader、Splitter、Embedding、Retriever、Prompt、模型、Tool 与输出解析等可组合能力。
2. LangGraph 负责 AgentState、节点、条件边、循环限制、Interrupt、Checkpoint 与恢复。
3. Chroma 只承担文本向量和检索元数据的保存与相似度检索。
4. SQLite 保存文档版本、入库任务、模拟业务数据，以及后续评估后适合落入关系存储的状态。
5. Provider 协议隔离通义千问 SDK，使 Fake Model、替换供应商和离线测试成为可能。
6. Streamlit 只负责交互展示，不承载必须执行的业务规则。

## 决策理由

### LangChain 与 LangGraph 分工

RAG 数据处理和模型调用适合使用 LangChain 的标准组件；人工确认、失败分支和恢复执行需要显式状态图。把两者分工可以避免用一个不可审查的 Prompt 隐式控制整个业务流程。

### Chroma

Chroma 可以本地持久化、接入成本低，适合第一版学习、评测和演示。项目会通过 retrieval 与 ingestion 模块封装访问，减少未来迁移到 Qdrant、Milvus 或 pgvector 时对业务层的影响。

### SQLite

文档版本、导入任务和业务实体需要事务、唯一约束与结构化查询，这不是向量库的主要职责。SQLite 无需独立服务，适合本地项目，并可通过 Repository 边界保留迁移空间。

### Streamlit

Streamlit 能快速完成聊天、知识管理和检索调试页面，使精力集中在 RAG 和 Agent 主链路。核心逻辑放在 UI 之外，以控制 rerun 带来的重复请求或重复写入风险。

### Python 3.13

Python 3.13 与当前本机目标环境一致。采用它可以暴露并解决真实兼容性问题，但每次引入核心依赖都必须执行安装与导入验证。若关键组件无法兼容，必须通过新的 ADR 记录是否降级到 Python 3.12，禁止静默切换。

## 考虑过的备选方案

### 方案 A：只使用 LangChain Agent

优点：

- 初始代码更少。
- 可快速演示工具调用。

未选择原因：

- 工单确认、失败恢复和循环限制不够显式。
- 关键业务顺序过度依赖 Prompt，难以证明模型不能绕过确认节点。

### 方案 B：完全自行实现 RAG 与状态机

优点：

- 依赖更少。
- 可以观察全部底层细节。

未选择原因：

- 会重复实现大量 Loader、Splitter、模型适配和图调度能力。
- 项目目标包括理解 LangChain 与 LangGraph 的职责边界。
- 学习收益与维护成本不匹配。

### 方案 C：使用托管向量数据库

优点：

- 更接近分布式生产部署。
- 可扩展性和远程访问能力更强。

未选择原因：

- 第一版文档规模与本地演示不需要远程服务。
- 增加账号、网络、费用和运维变量，会干扰核心链路学习。

### 方案 D：只使用向量库保存所有数据

优点：

- 存储组件更少。

未选择原因：

- 文档版本、任务状态、幂等键和业务数据需要关系约束与事务。
- 向量检索和结构化业务存储的查询模型不同。

### 方案 E：FastAPI 加独立前端

优点：

- API 与 UI 分离，更接近常见服务架构。

未选择原因：

- 第一版会显著增加前端与部署工作量。
- 当前目标是先完成可解释、可评测的 RAG 与 Agent 主链路。
- 核心模块保持与 UI 解耦，后续仍可添加 FastAPI。

## 后果

### 正面后果

- RAG 组件、Agent 编排、业务工具和 UI 有清晰边界。
- 写操作确认可以通过图结构和测试强制保证。
- Fake Model 与 Provider 接口降低网络依赖和供应商耦合。
- 本地存储方案便于学习、演示和自动化测试。
- 后续可替换模型、向量库或 UI，而不重写所有业务逻辑。

### 成本与风险

- LangChain 与 LangGraph 版本变化较快，需要锁定版本并记录兼容性。
- Python 3.13 可能缩小可用依赖版本范围。
- Chroma 与 SQLite 双存储会引入一致性问题，需要明确的入库状态和补偿机制。
- Streamlit rerun 可能造成重复请求，必须使用稳定请求 ID、Checkpoint 和幂等键。
- Provider 抽象会增加少量前期代码，但这是测试性和可替换性的必要成本。

## 实施约束

- 阶段 1 必须先验证 Python 3.13 下核心依赖的可安装与可导入版本，再固定依赖。
- 阶段 2 必须提供通义千问实现和无需联网的 Fake Model。
- 所有 Chroma 和 SQLite 路径必须由配置解析为明确的绝对路径。
- 模型不得直接获得创建工单的无条件执行能力。
- 任何替换关键技术或更改 Python 主版本的决定，都需要新增或取代本 ADR 的决策记录。

## 验证方式

该决策将在后续阶段通过以下证据验证：

- Python 版本、依赖安装和核心包导入检查。
- Fake Model 离线测试。
- 文档重复导入、更新和删除的一致性测试。
- 检索阈值、引用校验和拒答测试。
- LangGraph 路由、循环限制、Interrupt 和恢复测试。
- 创建工单在未确认、取消、确认和重试场景下的自动化测试。
- 干净环境 README 重建与 Docker Compose 启动测试。

## 重新评估触发条件

出现以下情况时重新评估本决策：

- 关键依赖长期无法支持 Python 3.13。
- 文档量或并发需求超出本地 Chroma/SQLite 的已测能力。
- 需要接入真实企业系统或部署为多实例服务。
- Streamlit 无法满足已确认的交互或安全要求。
- 模型 Provider 需要支持本地模型、多供应商路由或严格的数据驻留要求。
