# ADR-0004：界面只做展示与触发，状态分两层存放

- 状态：已接受
- 决策日期：2026-09-11
- 适用阶段：阶段 12 起
- 决策范围：Streamlit 界面结构、界面状态与 Agent 状态的边界、流式与引用校验的关系
- 关联决策：ADR-0003 会话记忆、ADR-0001 技术栈

## 背景

阶段 12 要交付对话页、知识库管理页与检索调试页，同时明确区分「UI 消息历史」与「Agent 持久化状态」，并避免 Streamlit rerun 造成重复请求或重复写。

已有的约束来自前几个阶段：

- 写操作有两道屏障（图上的边、工具层的 `confirmed`），阶段 11 又加了节点内 `interrupt()`。界面不能成为绕过它们的入口。
- 会话状态已经由 SQLite Checkpointer 按 `thread_id` 持久化，阶段 11 已验证跨进程恢复。
- 入库已经幂等：内容未变的文档会被短路，不重复调用 Embedding。
- 回答必须经过引用校验；流式输出不能跳过校验。

Streamlit 的 rerun 模型是这里的主要难点：每个交互都会从头重新执行整个脚本，包括入口文件。

## 决策

1. **界面不承载业务规则**。`ui/` 只调用 `agent/`、`tools/`、`memory/`、`ingestion/` 已经存在的入口，路由、确认门禁、幂等键、引用校验全部留在原处。
2. **用 `st.navigation` + `app_pages/` 组织三页**，`position="top"`。页面是普通脚本而不是渲染函数；入口 `app.py` 是路由与框架。
3. **状态分两层**：显示用的消息列表放 `st.session_state`；会话真相放 SQLite Checkpoint。侧边栏同时显示两者，并在界面上写明刷新页面会清空前者、不会影响后者。
4. **共享资源用 `@st.cache_resource`**（带 TTL 与释放回调）持有向量库、模型客户端与三个 SQLite 句柄；每用户数据一律放 `st.session_state`，不放在模块级变量里。
5. **知识库页在每次 rerun 重新读取真实状态**，不缓存文档列表；上传这类重活由表单提交触发，结果放进一次性会话值并在下一次渲染时弹出，避免 rerun 重复执行。
6. **流式输出用 `st.write_stream` 的等价做法展示进度，但用户看到的是通过校验的答案**。具体做法是 `stream_chat_turn` 先产出原始增量（用于状态提示），最后产出经过 `finalize_answer` 校验的 `ChatTurn`；页面渲染 `turn.run.answer`，绝不渲染原始流。
7. **界面区分「本轮回合」与「整条会话」**。`ChatTurn` 新增 `turn_trace` 与 `turn_tool_results`，由调用前后捕获的通道长度切分得出。

## 决策理由

### 为什么业务规则一行都不搬进界面

如果界面自己判断「能不能写」「要不要确认」，那么 CLI 与界面就会有两套规则，而阶段 10 的结构性证明（图的边集合里不存在直达创建的边）就只覆盖其中一条路径。界面复用同一批入口后，「界面绕过确认门禁」在结构上不可能发生——因为它根本没有自己的写路径。

### 为什么页面是脚本而不是函数

Streamlit 官方最佳实践明确把「把页面主体包进 `render()` 再调用」列为反模式：页面文件本身就是被执行的脚本。遵循这一点也让 `AppTest` 的 `switch_page` 能按文件名定位页面。

### 为什么显示状态与 Agent 状态必须分开讲

`st.session_state` 属于一个浏览器会话：刷新即丢。Checkpoint 属于数据：换了浏览器、重启了服务都还在。这两者在界面上必须有可见的区别，否则会出现「我明明看到它说过，怎么它忘了」这类误判。侧边栏把「界面消息数」与「Checkpoint 检查点数」并列显示，并在说明里点明刷新后的行为，就是为了消灭这个歧义。

反过来也不能把 `st.session_state` 当作会话真相：阶段 14 要做的 Streamlit 状态与 Agent 状态对接，前提是知道两者不是一回事。

### 为什么流式不能直接渲染模型输出

本项目的回答格式是 JSON（`status`/`answer`/`citations`），而且引用编号要经过越界校验，没有可核验引用的回答必须被拒答。因此原始流不能给用户看：它既不是最终答案，也尚未通过校验。把增量当作**进度信号**、把校验后的文本当作**答案**，是唯一同时满足「真流式」与「拒答可靠」的做法。

### 为什么需要「本轮回合」这个视图

Checkpoint 里存的是累积值：`trace` 与 `tool_results` 会带着整条会话的历史一起返回。CLI 直接打印累积值（阶段 11 已观察到这个现象），界面上会更严重——用户会以为这一轮又重跑了设备查询和订单查询。因此由代码在调用前后记录通道长度，切出本轮的增量。这不是美化，是避免界面陈述错误的事实。

### 为什么可能为空的相对指标要特殊显示

检索页在只有一个命中时前两名分差为 `None`，直接格式化会抛异常（这是实现过程中真实发生的崩溃）。这类「只有一条数据时没有意义的相对指标」必须显示为「不适用」，而不是显示 `0` 或让页面报错。

## 考虑过的备选方案

### 方案 A：为界面单独写一套业务逻辑

被否。会立刻产生两套规则，且界面路径无法继承阶段 10、11 的结构性证明与测试。

### 方案 B：用 `st.session_state` 存会话状态，不接 Checkpoint

被否。那样「服务重启后能继续会话」这条阶段 11 验收条件在界面上直接失效，界面会变成比 CLI 更弱的入口。

### 方案 C：界面直接展示累积的 `trace` 与 `tool_results`

被否。会把历史当成刚刚发生的事实，属于界面在陈述错误信息。

### 方案 D：为界面加一个 `st.App` ASGI 入口以便 `python -m` 启动

被否。Streamlit 文档明确把 `st.App` 限定在需要自定义路由、中间件等 ASGI 能力的场景，并建议简单应用用 `streamlit run`。本项目不需要那些能力，增加入口只会多一处可能失效的启动方式。

## 后果

正面：

- 界面与 CLI 走同一套规则，界面无法绕过写门禁；确认与取消在界面上有真实效果（实测：取消后工单数不变，确认后为 1）。
- 知识库页的上传真的走通入库管线并写入 `data/raw/`。
- 流式与引用校验可以同时成立。
- 界面不会把整条会话的历史误报为本轮活动。

负面与限制：

- 界面没有身份认证：侧边栏的「用户编号」只是演示标识，任何访问者都能填任意编号。真正的认证属于后续阶段，README 与界面上都写明了这一点。
- `AppTest` 无法覆盖图表/表格选择事件、自定义组件 JavaScript 与最终视觉效果，这部分只能人工查看页面；测试文件里明确写出了这个边界。
- 为让 Streamlit 的 rerun 能在不同线程里使用 SQLite 句柄，`MetadataStore` 与 `BusinessRepository` 改为 `check_same_thread=False` 加可重入锁，并启用 WAL。同一进程内的并发写入因此是串行的，吞吐上限受此约束；这是本地演示定位下的取舍。
