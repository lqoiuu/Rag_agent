# ADR-0002：模型接入层采用自定义协议、httpx 直连兼容端点并同步优先

- 状态：已接受
- 决策日期：2026-09-10
- 适用阶段：阶段 2 起
- 决策范围：聊天模型与 Embedding 的接入方式
- 关联决策：ADR-0001 技术栈

## 背景

阶段 2 要求定义聊天与 Embedding Provider 协议，实现通义千问适配器，提供可离线运行的 Fake Model，完成最小 Prompt -> Model -> Parser 链路，并统一超时、重试、错误分类和耗时记录。ADR-0001 已经确定“通义千问作为首个实现，外部包裹自定义 Provider 协议”，但没有决定用哪种方式访问通义千问。

主要约束：

- 业务代码不能绑定单一供应商（ADR-0001）。
- 核心依赖必须在 Python 3.13 下可用，且尽量少引入新依赖。
- 核心逻辑必须能在无网络、无密钥的环境中测试。
- 模型故障要有明确且可测试的错误语义，不能用字符串互相区分。

## 决策

1. 用 `typing.Protocol` 定义 `ChatModel` 与 `EmbeddingModel`，不引入任何模型 SDK。
2. 通义千问适配器通过 httpx 直接调用 DashScope 的 OpenAI 兼容端点：`/chat/completions` 与 `/embeddings`。
3. 阶段 2 只提供同步接口，异步推迟到确有并发需求的阶段。
4. 模型错误分成七类（超时、连接、限流、服务端、鉴权、请求、响应），每类显式声明 `retryable`。
5. `latency_ms` 与 `attempts` 作为返回值的一部分，而不是只写日志。
6. 缺密钥或密钥为空白时在构造阶段就失败，不发出任何请求。
7. Fake 实现必须是确定性的，并能按脚本注入错误，以便测试重试路径。

## 决策理由

### 为什么不用官方 dashscope SDK

SDK 会再引入一层需要跟随版本变化的抽象，而阶段 2 真正需要的只是两个 HTTP 端点。SDK 也不能免除“提供 Fake 才能离线测试”的工作，反而会让测试替身需要模拟 SDK 对象。兼容端点是稳定的 HTTP 契约，用 httpx 调用后，请求构造、超时、重试和错误分类全部由项目自己掌握，正好覆盖阶段 2 的核心学习目标。

### 为什么不直接用 langchain-openai

项目确实需要在阶段 2 练习 LCEL，但 LCEL 由已经安装的 `langchain-core` 提供（`RunnableLambda` 等），不需要 `langchain-openai`。若使用 `ChatOpenAI`，错误语义会变成第三方异常体系（OpenAI SDK 的异常类），“统一错误分类”这条要求就得再包一层适配，等于多做一层却不增加学习价值，同时还要新增 openai SDK 依赖。

### 为什么同步优先

阶段 2 没有任何并发等待场景：一次问答就是一次请求。异步的价值出现在 Token 流式输出和批量入库，而这两件事的调用方式（LangGraph 节点、Streamlit、入库批处理）要到后续阶段才确定，现在猜测异步边界容易做错。代价是阶段 7 引入流式时需要补一层异步适配，这个代价是明确且可控的。

### 为什么 `retryable` 必须显式声明

超时、连接失败、限流和服务端错误属于暂时性故障，重试有成功可能；鉴权、请求格式和响应结构问题属于语义性故障，重试一万次结果相同，还可能产生费用或触发风控。把这条规则写进错误类型而不是散落在调用点，才能用测试逐条证明。

### 为什么 Fake 必须确定性

相同文本必须得到相同向量，否则阶段 6 的阈值与排序断言、阶段 8 的可重复评测都会变成偶发失败。用脚本注入错误序列则让重试次数这类断言可以精确表达。

## 考虑过的备选方案

### 方案 A：官方 dashscope SDK

优点：接口与官方文档最贴近，参数覆盖最全。

未选择原因：耦合更深，替换供应商时改动面更大；离线测试仍需自建替身；错误分类要额外包一层。

### 方案 B：langchain-openai 指向兼容端点

优点：直接复用 LangChain 生态，聊天与 Embedding 都现成。

未选择原因：第三方异常体系外泄，削弱统一错误语义；新增 openai SDK 依赖；LCEL 学习目标由 langchain-core 单独满足。

### 方案 C：httpx 直连兼容端点（已选择）

优点：零模型 SDK 依赖；请求、超时、重试、错误分类全部自主可控；离线测试只需替换 httpx 传输层。

缺点：兼容端点的字段变化需要项目自己兜住，用 Pydantic 校验响应结构来兜底。

### 方案 D：完全自建 HTTP 客户端

优点：连 httpx 都不需要。

未选择原因：连接池、重定向、代理、超时语义都要自己实现，属于重复造轮子，且 httpx 已经是项目的直接依赖。

## 后果

### 正面后果

- 模型层没有任何供应商 SDK 依赖，替换供应商只需新增一个 adapter 模块。
- 错误语义和重试策略由项目定义，可以逐条测试。
- 无网络、无密钥即可运行全部核心测试，测试结果稳定可复现。
- 耗时、重试次数和 token 用量从阶段 2 起就被记录下来，后续评测和可观测性阶段不需要回头改接口。

### 成本与风险

- 需要自行维护兼容端点的响应解析，字段变化会以 `ModelResponseError` 暴露。
- 兼容端点的行为可能与官方 SDK 存在差异，遇到差异时以实际响成为准并补充测试。
- 同步接口在阶段 7 的流式输出场景需要补充异步实现。
- 日志目前只记录非敏感指标；更完整的上下文脱敏在阶段 13 完成。

## 实施约束

- 业务代码只允许依赖 `rag_agent.providers.base` 中的协议与错误类型。
- 密钥只能经 Settings 从环境变量或本地 `.env` 读取，禁止出现在日志和返回值中。
- 模型实例由 `config/providers.py` 依据 Settings 组装，适配器不感知应用配置。
- 任何新增供应商实现都必须提供对应的确定性 Fake 与离线测试。

## 验证方式

- `tests/unit/test_provider_errors.py`：状态码到错误类型的映射、重试次数、可重试契约、错误信息不泄露密钥。
- `tests/unit/test_qwen_adapter.py`：请求 URL、鉴权头、请求体、响应解析、批次数与维度校验。
- `tests/unit/test_provider_factory.py`：配置到模型实例的组装与缺密钥行为。
- `tests/unit/test_fake_providers.py`、`tests/unit/test_minimal_chain.py`：离线链路与协议可替换性。
- `tests/integration/test_qwen_live.py`：真实模型联网调用，默认跳过。

## 重新评估触发条件

- 阶段 7 需要模型 Token 流式输出。
- 阶段 5 的批量入库需要并发 Embedding。
- 兼容端点缺少项目需要的参数，例如 Embedding 维度控制或多模态输入。
- 需要多供应商路由、本地模型或严格的数据驻留要求。
